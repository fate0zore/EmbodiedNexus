## 一、项目定位与总体架构

EmbodiedNexus 面向具身智能算法开发，提供统一、可配置的设备读取与操作接口，使算法能够快速接入机器人、部署实验并验证效果。

Arachne 作为首个适配平台，首期覆盖 Scout 底盘、Aubo i5 机械臂、MS42DC 夹爪、Gemini335 相机和 C16 雷达。系统从现有代码中抽取成熟驱动，在 EmbodiedNexus 中独立运行。

核心验收目标：

- 每种设备可以独立配置、启动、读取、操作和停止。
- ROS 2 节点与远程 Python 算法使用相同的设备能力和控制规则。
- 算法通过配置选择设备实例，硬件地址、型号和驱动细节留在适配层。
- 同一个算法示例可以切换真实与 mock 后端。
- 实验能够保存实际配置、标定和版本信息，便于复现。

系统划分为五层：

| 层级             | 主要职责                                 | 边界                           |
| ---------------- | ---------------------------------------- | ------------------------------ |
| 算法接入层       | Python SDK、ROS 2 接口、算法接入示例     | 使用设备能力，声明输入输出需求 |
| 通信层           | 远程控制请求、状态与传感器数据传输       | 转发请求，不直接访问硬件       |
| 设备服务层       | 能力查询、状态、控制权、操作执行与取消   | 对两类调用方执行一致的规则     |
| 驱动适配层       | 设备协议、厂商 SDK、数据转换、连接恢复   | 封装具体设备差异               |
| 硬件与平台配置层 | 连接参数、设备组合、安装关系、标定和约束 | 描述实际机器人及实验环境       |

机器人端基于 ROS 2 Humble 运行。每种设备具有独立进程和启动入口；远程网关通过 ROS 2 调用设备服务。Python SDK 不依赖 ROS，支持同局域网 Windows/Linux 客户端。

首期提供基础控制与运动原语。抓取、道路清理、路径规划、笛卡尔运动规划和示教界面作为后续上层模块接入。

## 二、设备解构与统一接口

### Arachne 代码抽取原则

当前代码已具有驱动基础，但示教面板、抓取流水线和任务服务仍包含设备能力。抽取时按能力归属拆分：

- 将 Aubo RPC、上下电、模式切换、关节运动和速度控制收拢到机械臂设备服务。
- 将底盘相对移动、转向与停止从抓取任务服务中抽出。
- 保留底盘、夹爪现有串口协议实现，分离协议处理与 ROS 接口。
- 相机、雷达独立于面板、抓取服务、RViz 和 Nav2 启动。
- 提取机器人模型、坐标变换和标定读取能力，支持无界面运行。
- 统一设备状态来源，移除新系统中通过面板或可视化模块补充硬件状态的依赖。
- 抽取代码时记录来源提交和许可证；新运行栈不依赖原项目目录或构建产物。

### 五类设备的首期能力

| 设备       | 读取能力                          | 操作能力                                   | 主要配置项                                |
| ---------- | --------------------------------- | ------------------------------------------ | ----------------------------------------- |
| 底盘       | 里程计、速度、连接及运行状态      | 速度控制、相对直行、相对转向、停止         | 串口/CAN 参数、限速、超时、里程计与坐标系 |
| 机械臂     | 关节位置/速度、运行模式、安全状态 | 关节目标、关节速度、上下电、示教模式、停止 | 地址、关节映射、运动约束、工具负载、超时  |
| 夹爪       | 连接状态及硬件实际提供的反馈      | 开合、停止、已有的角度控制                 | 串口、设备编号、行程或角度范围、速度      |
| RGB-D 相机 | RGB、深度、内参、采集状态         | 启停采集、查询与调整支持的采集参数         | 设备标识、分辨率、帧率、编码、坐标系      |

设备只能声明真实支持的能力。缺少实测位置或力反馈时返回“未知”，不以命令目标代替测量值。

### 公共接口模型

建立版本化的设备公共契约：

- `DeviceDescriptor`：设备标识、类型、驱动与接口版本、支持的能力。
- `DeviceState`：连接状态、运行状态、数据时间戳、健康状态与故障信息。
- `CapabilityDescriptor`：操作或数据流名称、参数、单位、范围及可用条件。
- `OperationHandle`：持续操作的标识、进度、结果、取消和超时。
- `ControlLease`：执行设备控制权及有效期。
- `ConfigSnapshot`：最终生效配置、配置版本和标定引用。

ROS 2 使用标准消息传输图像、点云、里程计和关节状态；使用 service 管理配置、控制权和模式，使用 action 执行可取消的持续操作。命令接口携带控制权标识。

Python SDK 按设备类型提供接口，例如：

```python
robot.devices.list()
robot.arm("arm_main").get_state()
robot.base("base_main").move_relative(...)
robot.camera("camera_front").subscribe(...)
```

SDK 的持续操作返回可等待、查询和取消的句柄。首期不构建算法调度框架，通过最小示例说明算法如何声明设备需求、订阅数据和发送动作。

## 三、配置体系与扩展机制

配置是一等能力，与设备接口一起设计。采用 YAML 保存非敏感配置，使用明确的结构和类型校验。

### 配置分层

| 配置层       | 内容                                             |
| ------------ | ------------------------------------------------ |
| 驱动默认配置 | 驱动通用默认值、可调参数及有效范围               |
| 设备实例配置 | 设备 ID、驱动选择、地址、串口、设备专属参数      |
| 平台配置     | 设备组合、安装关系、坐标系、标定和平台安全约束   |
| 实验配置     | 算法使用的设备绑定、订阅频率、运行参数及输出目录 |

优先级为：驱动默认值 → 设备与平台配置 → 实验覆盖 → 显式启动参数。后两层只能覆盖声明为可覆盖的字段；设备安全上限不允许由实验配置扩大。

凭据和访问令牌通过环境变量或本机独立文件注入，配置快照仅保存脱敏后的引用。

### 自定义与校验规则

- 公共参数使用统一语义；厂商专属参数放入对应驱动的扩展区。
- 每个驱动提供参数描述，包括类型、单位、范围、默认值与生效方式。
- 参数分为启动时设置、停机后调整、允许运行时调整三类。
- 未知公共字段、无效参数组合和不支持的能力在启动前报告。
- 配置变化由设备服务统一处理，返回成功、拒绝或需要重启；不允许部分失败后仍报告整体成功。
- 控制相关配置调整需要设备控制权；采集参数调整需要设备处于允许重新配置的状态。
- 提供配置检查、最终配置查看和配置差异比较命令。

### 设备替换与新增适配

算法以“逻辑角色”绑定设备，例如前视相机、主机械臂和移动底盘。角色映射到具体设备实例，避免算法写死设备地址或厂商名称。

新增驱动遵循统一适配契约，实现连接、关闭、能力描述、状态读取、支持的操作及停止处理。通过包注册发现驱动，不修改公共核心的设备型号判断分支。

允许同时存在多个同类设备；每个实例使用唯一设备 ID、独立配置和命名空间。

真实与 mock 后端保持公共契约一致。mock 明确声明模拟数据与能力范围，支持断连、超时和故障注入。

## 四、控制、数据传输与运行管理

### 控制权与停止机制

每个执行设备只允许一个控制权持有者，ROS 与远程 Python 参与同一仲裁。

- 租约默认每 0.5 秒续约，2 秒过期。
- 速度命令另设本体 watchdog，初值沿用现有驱动配置。
- 租约失效、命令超时或状态不满足运动条件时，设备服务取消相关操作并请求停止。
- 已认证客户端均可读取状态和请求停止；运动、模式切换和上下电需要控制权。
- 重连后重新申请控制权，不恢复中断前的运动命令。
- 设备启动默认禁止运动，显式启用后才接受运动命令。
- 保留 Aubo 的示教、运行模式与安全状态检查，统一落实在设备服务内部。
- 软件停止请求、执行结果和硬件急停状态分别表达，避免混淆。

新旧运行栈互斥占用同一硬件。启动前检查已知进程及设备资源占用，发现冲突时报告并退出，不自动终止其他运行栈。

### 远程通信与实时数据

远程接口采用版本化 HTTP JSON 控制接口和 WebSocket 数据流；机器人端使用 Starlette/Uvicorn，SDK 使用 `httpx` 与 `websockets`。

- HTTP 与 WebSocket 使用统一令牌认证。
- 网关只调用设备服务，不直接打开串口或建立厂商 SDK 控制会话。
- 控制请求与大数据流分开处理，避免图像传输阻塞停止或取消请求。
- RGB 默认使用 JPEG；深度无损传输；点云和激光使用二进制载荷。
- 数据携带设备 ID、序号、采集时间、坐标系、单位和编码。
- 每个订阅采用有界队列，慢客户端丢弃旧帧并报告丢帧统计。
- 支持配置订阅频率和降采样，不改变设备原始采样配置。
- 保留各数据源原始时间戳；首期提供基于时间戳的近似配对，不宣称 RGB、深度及雷达硬件同步。

### 生命周期与可观测性

设备状态统一表达为未连接、连接中、就绪、运行中、故障和关闭；运动使能单独表达。

单设备故障应限制在该设备进程内。驱动可按配置尝试重连，重连后重新建立状态与控制条件。

统一输出设备日志、连接次数、数据频率、数据年龄、操作耗时、失败原因和控制权状态。每次实验保存配置快照、驱动版本、代码版本及标定版本。

首期使用 CLI 和 ROS launch 管理运行，不默认安装开机自动运动服务。

## 五、实施阶段、交付与验收

### 阶段 1：基线与公共契约

梳理 Arachne 有效驱动、真实启动参数、设备标识、反馈能力、标定与依赖。建立接口、配置结构和 mock，先验证两种调用方共享同一套行为。

交付：设备清单、代码抽取清单、接口文档、配置示例、mock 示例。

### 阶段 2：执行设备独立化

按底盘、夹爪、机械臂顺序抽取驱动和运动原语，完成控制权、停止、取消、超时与状态统一。

交付：三类设备独立启动入口、ROS 接口及 Python 控制示例。

### 阶段 3：传感器独立化与实时传输

接入相机、雷达、内外参与 TF，完成远程数据订阅、订阅限频和慢客户端处理。

交付：独立采集入口、实时读取示例、数据格式与时间戳说明。

### 阶段 4：算法接入与实验复现

提供一个统一验证示例：从配置选择设备，持续读取数据，申请控制权，执行有界动作并保存运行记录。分别使用 ROS 与 Python 调用，支持真实/mock 配置切换。

交付：算法接入指南、平台配置模板、实验配置模板与运行报告。

### 验收标准

- 五类设备均可独立运行；其他设备缺席不会阻止其启动。
- 更换地址、串口、采集参数和设备角色绑定无需修改算法代码。
- 同一算法示例切换真实/mock 后端无需修改业务逻辑。
- ROS 与 Python 的操作结果、错误、控制权及取消行为一致。
- 覆盖配置错误、能力缺失、控制权冲突、状态陈旧、断连、租约过期及网关退出。
- 覆盖多传感器订阅和慢客户端，确认队列有界、控制请求可正常处理。
- 实机逐设备核对方向、单位、坐标系、反馈与停止效果；真实运动验收在用户明确确认机器人就绪后进行。
- 测量实际帧率、延迟、丢帧、带宽和本体负载，依据测量结果确定默认运行配置。

首期默认环境为本体 Ubuntu 22.04 / ROS 2 Humble，以及同局域网 Windows/Linux、Python 3.10 及以上客户端。原 Arachne 和未提交的示教记录保留，作为功能对照与后续上层模块迁移来源。
