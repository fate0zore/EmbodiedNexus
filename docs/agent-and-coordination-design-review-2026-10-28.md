# 智能体与多单元协调接入设计评估

日期：2026-10-28  
范围：当前工作区源码、配置及现有设计和验收文档；Git 基线 `d65fbee`，工作区另有用户未提交变更。本次只作静态阅读，未运行代码、测试、构建、仿真或实机，也未测量性能。以下结论是设计和实现可行性判断，不代表新的运行验收。

## 结论

当前项目可以作为智能体和协调算法的**设备接入层**：远程 Python 或 ROS 程序可以发现设备、读取状态与传感器数据、申请单设备控制权、发起运动并查询或取消操作。上层自行编排后，可尝试观察—决策—动作和底盘、机械臂、夹爪的顺序协作。已有仿真验收文档报告了单机器人顺序协作，但这不是本次复验，也不能推导为多机器人或实机能力。

目前还不能把它视为现成的多单元协调控制平台。设备租约和操作作用于单设备，缺少跨设备任务状态、组合资源获取、统一失败处置以及多机器人身份、时间和坐标约定；现有接口也没有承诺确定性时延或同步启动。LLM 智能体可以作为上层决策者，运动执行仍需经过确定性的任务执行器和设备服务。紧耦合闭环、双臂协同、车队编队等应先补齐契约并完成测量，不宜直接依据现有 HTTP/SDK 路径假定可用。

| 场景 | 静态评估 | 主要前提或缺口 |
| --- | --- | --- |
| 智能体查询设备、观察、选择低频动作 | 有接入基础 | 上层需处理能力差异、状态时效、超时与失败；动作需独立约束 |
| 单机器人底盘、臂、夹爪顺序任务 | 有接入基础，需自行编排 | 单设备租约和操作句柄不能自动形成任务事务；历史仿真记录有顺序协作 |
| 跨设备并发或移动操作 | 有底层原语，不能保证协同 | 缺组合占用、空间约束、联动停止及同步时序 |
| 多机器人任务分配与低频协作 | 可在多个 Core 之上构建 | 需全局身份、发现、状态聚合、资源仲裁与故障隔离 |
| 高频闭环、严格同步或安全相关协同 | 暂无依据认定满足 | 需明确控制周期、抖动、时钟误差、网络故障行为并实测；必要时在机器人侧实现闭环 |

## 现有基础与证据

1. **设备与算法边界清晰。** [总体规划](../todo/设备中间层总体规划.md)定位为设备读取与操作中间层，明确首期不构建算法调度框架。[架构说明](architecture.md)规定设备独立、通过公开 ROS 或远程接口协作；这适合把智能体、规划和协调器作为独立上层，而不是放进硬件驱动或 Core。
2. **统一入口和多实例已有基础。** [Core 配置](../src/core/embodied_nexus_core/embodied_nexus_core/config.py)允许同一平台列出多个不同 ID 的同类设备，并校验设备配置身份；[Core SDK](../sdk/python/embodied_nexus_client/core.py)按 ID 返回各设备客户端。Core 管理进程和代理设备接口，`start_all`、`stop_all` 是管理操作，不是跨设备协调动作。设备类型在 Core 中由固定映射登记，增加全新设备类型仍需扩展该映射。
3. **单设备控制原语较完整。** [底盘节点](../src/base/embodied_nexus_base/embodied_nexus_base/base_node.py)和[机械臂节点](../src/arm/embodied_nexus_arm/embodied_nexus_arm/arm_node.py)提供信息、状态、控制租约、使能、停止及 ROS action；[机械臂控制器](../src/arm/embodied_nexus_arm/embodied_nexus_arm/controller.py)包含租约、反馈新鲜度、运动检查和速度 watchdog。SDK 的[底盘](../sdk/python/embodied_nexus_client/base.py)、[机械臂](../sdk/python/embodied_nexus_client/arm.py)和[夹爪](../sdk/python/embodied_nexus_client/gripper.py)提供租约续期和操作句柄。停止请求、写入零速、静止确认、硬件急停等反馈需要分别判断，例如[底盘状态消息](../src/base/embodied_nexus_base_interfaces/msg/BaseState.msg)和[机械臂 action](../src/arm/embodied_nexus_arm_interfaces/action/MoveArmJoints.action)分别表达这些字段。
4. **观察数据与仿真有基础。** [相机流](../src/camera/embodied_nexus_camera/embodied_nexus_camera/web_server.py)提供序号、时间戳来源、frame、编码和标定版本；[雷达流](../src/lidar/embodied_nexus_lidar/embodied_nexus_lidar/web_server.py)携带时间戳和坐标系。ROS 侧还有里程计、关节状态和 TF 等数据。[仿真记录](../src/sim/gazebo/embodied_nexus_sim_gazebo/docs/acceptance-20261024.md)记载单机器人底盘避障、机械臂和夹爪顺序协作，以及暂停、时钟回跳等故障语义；该记录也明确列出帧率、模型及真实设备覆盖限制。

## 主要缺口与影响

### 1. 跨设备任务与资源：优先级高

设备租约分别获取，不能保证同时占有一组设备；获取部分成功后，后续设备被占用、续租失败、网络中断或动作失败时，上层必须决定如何释放和停止。[Core 管理器](../src/core/embodied_nexus_core/embodied_nexus_core/manager.py)的批量停止并发调用各设备，结果是逐设备反馈，并不意味着同时停止或所有设备均已静止。单设备动作也无法表达任务级前置条件、依赖、补偿和整体结果。

建议独立协调器先实现最小任务状态机：按固定顺序获取所需租约，部分失败时释放已获取租约；记录每项操作 ID、开始和终态；任一关键动作失败或续租失效时取消相关操作、逐设备请求停止，分别核验停止反馈；无法确认静止时保留未知状态并阻止自动续作。物理动作不可简单回滚，补偿必须由具体任务定义。上述组合获取是上层协议，不应宣称为原子事务。

### 2. 多机器人身份和隔离：优先级高

平台配置仅描述本 Core 管理的设备 ID、类型及配置，并无机器人 ID、跨平台注册、角色绑定或拓扑模型。设备 ROS 路径如[底盘节点](../src/base/embodied_nexus_base/embodied_nexus_base/base_node.py)和[机械臂节点](../src/arm/embodied_nexus_arm/embodied_nexus_arm/arm_node.py)使用绝对 `/embodied_nexus/...` 路径；Core 的 ROS 管理服务也使用固定绝对路径。两台机器人分开运行各自 Core 并由上层按 URL 区分是一种可行的接入方式，但在同一 ROS 图合并时，重复设备 ID、Core 服务和 TF frame 可能冲突；具体隔离效果仍需在目标部署验证。[仿真 launch](../src/sim/gazebo/embodied_nexus_sim_gazebo/launch/sim.launch.py)当前使用固定单机器人实体和命名空间，不能据此认定现成支持多机器人场景。

建议先约定全局 `(robot_id, device_id)`、Core 地址与逻辑角色映射，明确 ROS 域或命名空间和 frame 的隔离方案。跨机器人共享地图或目标时，显式维护机器人间坐标变换与其来源、版本和有效期；不要把不同机器人的 `odom` 直接当作同一坐标系。

### 3. 时间、坐标和观测一致性：优先级高

单帧携带时间戳不等于多设备同步。[相机节点](../src/camera/embodied_nexus_camera/embodied_nexus_camera/camera_node.py)存在主机接收时间、ROS header 和 mock 时钟等来源；[雷达流](../src/lidar/embodied_nexus_lidar/embodied_nexus_lidar/web_server.py)标记驱动 header；[机械臂控制器](../src/arm/embodied_nexus_arm/embodied_nexus_arm/controller.py)也区分反馈时间来源。跨主机时钟偏差、传输延迟、数据年龄和 TF 有效性都影响抓取和避障。现有平台配置没有统一描述跨设备安装关系或可供协调器使用的融合快照契约；不代表单设备没有标定或 TF 功能。

建议为每个任务规定最大数据年龄、允许的跨源时间差、时钟域与偏差预算，并对缺失或过期的变换拒绝执行；记录采集时间、接收时间、来源、frame、标定版本和质量。先在机器人侧实现按时间配对的观测层，再按任务需求暴露快照；不要声称软件配对等同硬件同步。

### 4. 动作粒度和实时性：优先级高

机械臂公开关节目标与关节速度，底盘公开速度、相对位移和转向；例如[机械臂 action](../src/arm/embodied_nexus_arm_interfaces/action/MoveArmJoints.action)没有跨设备共同启动时间或轨迹同步字段。当前公开原语不能直接表达笛卡尔轨迹、整机碰撞约束或多设备同步轨迹；上层需要规划器及机器人模型，并将结果转为设备支持的动作。SDK 使用同步 HTTP 请求与操作轮询，具体速率和抖动没有本次测量，不能推定满足某个控制周期。历史仿真验收中满载相机样本约 1.9 FPS，仅是当时环境的观察，不能外推到目标设备。

建议低频任务通过 SDK/ROS action 编排；对快速闭环，先定义周期、端到端延迟、抖动、丢包和超时预算，再测量决定是否将控制回路放在机器人本地。双臂或移动操作如需时间同步执行，应单独设计控制器和协议，并验证控制器能力；并发发送请求不等于同步执行。

### 5. 智能体工具契约与权限：优先级中高

设备 `info` 和状态可作为工具适配依据，但当前不同设备的参数、结果和异常并非一套完整的机器可消费工具模式；例如[机械臂能力](../src/arm/embodied_nexus_arm/embodied_nexus_arm/controller.py)包含能力名称，而操作参数和约束仍需结合接口、配置及设备状态。SDK 很多结果为字典，智能体不能仅凭名称判断范围、单位、前置条件或停止是否确认。

[Core Web 入口](../src/core/embodied_nexus_core/embodied_nexus_core/web_server.py)使用共享 token 认证并代理设备；这提供入口认证，但从该入口代码不能推导出按智能体身份、设备和动作划分的权限或任务审计。设备租约解决占用，不等同身份授权。ROS 入口与远程入口的访问边界也需在部署时分别确认。

建议先包装少量明确的工具：观察、查询能力、申请任务、执行有界动作、查询、取消；为每项定义参数类型、单位、范围、所需设备、前置条件、超时和结构化结果。由确定性执行器验证决策、控制租约和状态，智能体只提交受限意图；按实际部署需要配置身份、权限及任务审计，避免将管理和全部运动权限直接交给模型。

### 6. 可复现性与故障恢复：优先级中

总体规划要求保存配置、版本和标定；当前可读取平台配置和设备状态，但本次静态阅读未发现覆盖跨设备任务的统一实验记录、全局操作关联和恢复协议。网络超时可能使调用方不知道动作是否被接收，不能简单重试运动；控制器重启后的操作恢复、重复请求与去重语义也应逐项确认。

建议记录任务 ID、机器人/设备 ID、配置与标定版本、决策输入时间、操作 ID、结果及停止确认；超时后先查询已知操作和设备状态，无法判明时标记未知并进入人工或明确的恢复流程。按需要定义请求幂等键和重启后的持久化语义，不要假定现有接口已提供。

## 推荐实施顺序与验收

1. **最小智能体适配**：选一个只读观察工具和一个有界动作工具，在 mock 中检查能力、租约、状态新鲜度、拒绝原因、取消和停止结果；工具结果包含设备 ID 和操作 ID。
2. **单机器人任务执行器**：以“底盘到位 → 机械臂运动 → 夹爪动作”为例，加入固定顺序租约获取、步骤状态、超时与失败停止。覆盖部分租约获取失败、单设备断连、续租失败和停止未确认；核验每个设备的反馈，而非仅看批量请求返回。
3. **跨机器人低频协作**：两个独立 Core 绑定全局身份和角色，验证同名设备/坐标系隔离、任务抢占和网络分区；建立跨机器人坐标与时间误差预算。
4. **按算法需求扩展闭环**：先测目标环境中的传感器年龄、跨源偏差、控制往返、周期抖动及停止确认，再决定本地控制、轨迹控制或同步协议；测试条件和阈值由具体任务确定。
5. **分层验收**：依次做本地测试、Humble mock/仿真和目标机器性能测试；真实运动只在用户明确确认机器人就绪后进行，分别记录停止请求、静止确认和硬件急停状态。
